# TCP 二进制协议逆向入门（以坦克风暴为例）

写给"熟悉 HTTP、但没搞过裸 TCP"的人。全部例子都取自本项目真实抓包，可对照验证。

---

## 0. 先建立心智模型：HTTP 帮你做了什么

| | HTTP | 裸 TCP |
|---|---|---|
| 消息边界 | 协议规定好了（`\r\n\r\n` + `Content-Length`） | **没有**，只有一条连续字节流 |
| 语义 | 自描述（URL、方法、头部都是明文） | 全是自定义，得自己猜 |
| 一问一答 | 基本是 | 不一定，服务器可随时主动推送 |
| 内容 | 大多文本/JSON | 二进制，可能还带压缩或加密 |

**最重要的一句话：TCP 是字节流，不是消息流。**

你 `send()` 三次，对方可能一次 `recv()` 全收到（粘包）；你 `send()` 一次 5000 字节，
对方可能分四次才收全（拆包）。**TCP 只保证顺序和不丢，不保证边界。**
所以逆向的第一步永远是：**找出这个协议自己是怎么划分消息边界的。**

---

## 1. 第一步：找帧结构（framing）

常见就四种：

1. **长度前缀**（最常见）：开头 2 或 4 字节写明本条消息多长
2. **分隔符**：如 `\x00` 结尾（Flash 的 XMLSocket 就是）、`\n` 结尾
3. **定长**：每条消息固定字节数（少见）
4. **混合**：先定长头，头里带长度

### 怎么判断？拿流的开头几个字节试

坦克风暴客户端发的第一个真正的帧（心跳）：

```
00 06 04 0e 00 00 00 00        ← 一共 8 字节
```

推理过程：

- 前两字节 `00 06`。按**大端**读 = 6；按**小端**读 = 0x0600 = 1536。
  这个包总共才 8 字节，1536 明显不合理 → **大端**。
- 总长 8，长度字段说 6，8 − 6 = 2 → **长度字段不含自己**。
  所以规则是：`整帧 = 2 + N`。
- 拿另一条验证：`00 23 04 1c ...` 共 37 字节，0x23 = 35，2 + 35 = 37 ✓
  再验一条：`00 20 61 2c ...` 共 34 字节，0x20 = 32，2 + 32 = 34 ✓

三条都对，framing 就定了。**永远至少验三条不同长度的消息**，一条可能是巧合。

> 💡 如果长度字段怎么读都对不上，试试"长度包含自身"（`整帧 = N`），
> 或者前面还有几字节固定魔数（magic），把偏移挪一挪再试。

## 2. 第二步：写重组器（这是新手最容易翻车的地方）

知道了 framing，**不能**直接拿 `recv()` 的结果当一条消息用。必须缓冲：

```python
class FrameReader:
    def __init__(self):
        self.buf = bytearray()

    def feed(self, data):
        self.buf.extend(data)          # 先塞进缓冲区
        frames = []
        while len(self.buf) >= 2:      # 循环：一次可能吐出多帧
            n = int.from_bytes(self.buf[:2], "big")
            if len(self.buf) < 2 + n:  # 还没收全，等下一批
                break
            frames.append(bytes(self.buf[2:2+n]))
            del self.buf[:2+n]         # 消费掉
        return frames
```

关键点：

- **`while` 不是 `if`**：一次 recv 可能含多条完整消息
- **收不全就留着**：半条消息必须留在缓冲区等下次
- 本项目完整实现见 [`tankstorm/recorder.py`](../tankstorm/recorder.py) 的 `FrameReader`

> 我在测试里专门做了"逐字节喂入 300 字节大帧"和"一次喂入 3 帧"两种极端情况。
> 你自己写完也务必这样测——否则线上偶尔丢消息，你会找疯。

从抓包文件离线分析时同理：要先按 TCP `seq` 把整条流重组成连续字节，再切帧。
（我早期粗略解析没做重组，结果把 TCP 分段的中间部分误当成了 opcode，
冒出 `ffff`、`3433` 这种根本不存在的"消息类型"。这是个典型坑。）

## 3. 第三步：拆帧内结构

切出一帧后，看头几个字节哪些是"结构"、哪些是"数据"。坦克风暴：

```
00 06 | 04 0e | 00 00 00 00 | (body)
 长度 | opcode|    seq      |
```

**怎么认出 opcode 和 seq？靠对比：**

- **opcode**：把所有帧按这 2 字节分组，会发现少数几个值出现极多次
  （心跳 `040e` 出现 135 次），而且**同值的帧长度、结构高度相似** → 这就是消息类型
- **seq**：观察它是否**单调递增**。本例中服务器发来的 seq 是
  `0x247 → 0x248 → 0x249 …` 连续递增，而客户端发的 **seq 恒为 0**。
  这本身就是重要情报：说明服务器给消息编号、客户端不编号

**请求—响应配对**：客户端发 `040e`，服务器紧接着回 `0215`。
把时间轴上"我发 X → 它回 Y"的配对统计出来，就能画出协议的对话结构。

## 4. 第四步：识别 body 的编码

body 里常见几种：

| 特征 | 可能是 |
|---|---|
| 肉眼能看到 `{`、`<`、可读单词 | JSON / XML / 自定义文本 |
| 开头 `78 9c` / `1f 8b` | zlib / gzip 压缩 |
| 开头 `00 03` + `\x00\x0a` 等 | AMF（Flash 常用） |
| 大量 `08 12 1a 22 2a` 这类字节 + 夹杂可读字符串 | **Protobuf** |
| 完全高熵、同一操作每次都不同、无可读字符 | 加密 或 含随机数 |

### Protobuf 手工解码（本项目 body 就是它）

Protobuf 每个字段前有个 **key 字节**：

```
key = (字段号 << 3) | wire_type
```

wire_type：`0`=varint（整数/bool）、`1`=64位、`2`=长度分隔（字符串/嵌套消息）、`5`=32位

**实例 1** —— 登录认证包 `041c` 的 body：

```
1a 1b 52 65 64 77 61 72 68 71 32 30 31 38 ...
```

- `0x1a` = `0b00011_010` → 字段号 **3**，wire_type **2**（长度分隔）
- `0x1b` = 27 → 接下来 27 字节是内容
- 取 27 字节 = `"Redwarhq2018HoneyHoneyHoney"`（数一下正好 27）✓

解出来就是：**字段3 = "Redwarhq2018HoneyHoneyHoney"**

**实例 2** —— build 信息包 `041d` 的 body：

```
12 01 30 | 1a 05 6275696c64 | 22 09 756e646566696e6564 | 2a 09 ... | 30 00
```

- `12` → 字段2、类型2，长度 `01`，值 `"0"`
- `1a` → 字段3、类型2，长度 `05`，值 `"build"`
- `22` → 字段4、类型2，长度 `09`，值 `"undefined"`
- `2a` → 字段5、类型2，长度 `09`，值 `"undefined"`
- `30` → 字段6、类型0（varint），值 `0`

### 别手工硬啃，用工具

装了 protobuf 后，一行命令自动解析未知结构：

```bash
# 把 body 的 hex 转成二进制再喂给 protoc
python -c "import sys;sys.stdout.buffer.write(bytes.fromhex('1a1b52656477617268713230313848...'))" > body.bin
protoc --decode_raw < body.bin
```

输出形如：

```
3 {
  "Redwarhq2018HoneyHoneyHoney"
}
```

`--decode_raw` **不需要 .proto 文件**，是逆向未知 protobuf 的利器。

## 5. 核心方法论：差分分析（最重要的一节）

单看一条消息基本猜不出含义。**逆向的本质是对比。**

### 手法 A：同一操作做两次

同一个动作抓两遍，逐字节 diff：

- **完全相同** → 这条消息是静态的，可以原样重放（心跳就是这么确认的：
  抓包里 181 次心跳字节完全一致）
- **只有少数字节变** → 那几个字节是 序号 / 时间戳 / 随机数
- **整体都变** → 加密、压缩，或含随机 nonce

> 本项目实例：客户端的 `0422` 包，170 个里有 163 个各不相同。
> 这说明它**不能原样重放**——要么加密，要么含时间戳/随机数。
> 这就是我判断"心跳可复刻、0422 不可复刻"的依据。

### 手法 B：不同操作互相对比

做操作 A 抓一遍，做操作 B 抓一遍：

- **相同的部分** = 协议骨架（帧头、公共字段）
- **不同的部分** = 这个操作特有的数据

### 手法 C：控制变量

想知道某个字段是什么意思，就**只改那一个游戏内条件**再抓：
比如换个建筑、换个数量，看哪个字节跟着变。变化规律往往一眼可见
（数值 +1，字节就 +1）。

### 手法 D：建立"正常基线"，异常自然浮现

先在正常状态下跑一段时间，把出现过的 opcode 全记下来。
之后任何**不在基线里的 opcode** 就是新事件。
本项目就是这么做的：正常游戏 27 分钟提取出 61 种服务器消息类型，
写进 `recorder.py` 的 `KNOWN_OPCODES`，之后出现新类型立即告警。

## 6. 工具

### Wireshark（抓包必备）

- **过滤器**：`ip.addr == 1.2.3.4 && tcp.port == 8001`
- **Follow → TCP Stream**（右键菜单）：**最有用的功能**。
  它自动帮你做 TCP 重组，把整条流按方向着色显示，还能切换 Hex Dump 视图
- **Statistics → Conversations**：一眼看出哪条连接流量最大（通常就是主连接）
- 注意时间戳精度：Wireshark 常用纳秒，自己解析 pcapng 时要读
  `if_tsresol` 选项，否则时间会差 1000 倍（我在 `pcap_analyze.py` 里踩过这个坑）

### 本项目自带的

```bash
# 从 pcap/pcapng 定位登录握手和心跳（零依赖，不用装 scapy）
python tools/pcap_analyze.py 抓包.pcapng

# 分析运行时录制的帧日志
python tools/analyze_frames.py --around 21:52    # 某时刻前后
python tools/analyze_frames.py --unknown         # 只看没见过的消息类型
```

### 其他

- `protoc --decode_raw` —— 解未知 protobuf
- Python 的 `struct` 模块 —— `struct.unpack(">H", b)` 读大端 uint16
- CyberChef（网页版）—— 快速试各种解码/解压/解密组合

## 7. 实操流程总结

1. **确定目标**：找到游戏服务器的 IP 和端口（本项目是从网页的 FlashVars 里读到的
   `server=...&port=8001`）
2. **抓包**：Wireshark 挂过滤器，做一段有代表性的操作
3. **重组**：Follow TCP Stream，或自己按 seq 拼流
4. **定 framing**：从流开头试长度前缀，验三条以上
5. **切帧、统计 opcode**：哪些高频、哪些配对出现
6. **认 body 编码**：先看有没有可读字符串，再试 protobuf/压缩
7. **差分分析**：同操作两遍、不同操作对比，标注每个字段含义
8. **写客户端验证**：能连上、能跑通，才算真的懂了

---

## 8. 几个容易踩的坑

- ❌ 直接把 `recv()` 的结果当一条消息 → 必须缓冲重组
- ❌ 只验一条消息就下结论 framing → 至少验三条
- ❌ 忽略字节序 → 大端小端读出来天差地别
- ❌ 忘了服务器会**主动推送**（不是所有消息都是你请求的响应）
- ❌ 抓包时间戳精度没处理 → 算出来的间隔差 1000 倍
- ❌ 看到高熵就断定"加密了" → 也可能只是压缩，先试 zlib
