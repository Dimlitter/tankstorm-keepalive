## 游戏架构（抓包 + SWF 字节码双重确认）

坦克风暴是 Flash 游戏，主程序 `RedWar.swf` 通过裸 TCP socket 连到
`tankstorm-proxy.sincetimes.com:8001`（备用 443）跟服务器通信。

这带来几点结果。

- 游戏核心动作（含"在线状态"、签到、领奖、抽奖等）都走这条 socket，不是 HTTP。
  用 HTTP 抓包工具（浏览器 HAR、Fiddler、mitmproxy）抓不到它们，那些只能看到
  资源下载（.swf/.dat/图片）和 QQ 空间平台埋点。
- 保持活跃 = 维持这条 socket + 定时心跳。本项目用纯 Python `socket` 复刻它。
- 少数社交功能（好友赠礼/邀请/召回）确实是 HTTP `.war` 接口，可用 HTTP 脚本做。

> 勘误：本文档早期版本依据 `config.xml` 里的 `encrypt=false` 断言"协议未加密"，
> 这是错的。实际是 protobuf 序列化 + RC4 加密，只有白名单内的少数 opcode
> 走明文（见下方「协议与加密」）。当初之所以误判，是因为两个巧合：静态重放用到的
> 心跳/认证包恰好都在发送豁免名单里，能读到中文昵称的世界广播恰好在接收豁免名单
> 里，两者都推不出"协议没加密"。教训写在
> [protocol-reverse-engineering.md](protocol-reverse-engineering.md)。

登录参数链路（`tankstorm/qzone.py` 已实现，离线验证通过）：

```
game.qzone.qq.com/100616028   ← 带 QQ cookie 请求，Qzone 当场签发 openid/openkey
      │  <iframe data-src="https://tankstorm-qzone.sincetimes.com/?openid=..&openkey=..&pfkey=..">
      ▼
tankstorm-qzone.sincetimes.com/?openid=..   ← 外框页
      │  <param name="FlashVars" value="..&uid=..&secret=..&server=tankstorm-proxy.sincetimes.com&port=8001&sid=..&region=..">
      ▼
连 socket：tankstorm-proxy.sincetimes.com:8001
```

openid/openkey 每次由 Qzone 用登录 cookie 现签，保活守护进程能全自动拿到
新鲜票据，不需要人工交互。

## 协议与加密（抓包 + SWF 字节码还原）

```
protobuf 序列化 (com.netease.protobuf, BIG_ENDIAN)
        ↓
RC4 加密（仅 body，白名单 opcode 豁免）
        ↓
包头 [2字节大端长度 N][2字节 opcode][4字节 seq] —— 永远明文
        ↓
裸 TCP socket
```

整帧长 `2 + N`，长度字段不含自身；客户端所有包 `seq` 恒为 0，服务器 `seq` 单调递增。

登录序列有 4 步，写在 `protocol.json` 里：TGW 网关头 → `a,{uid},{secret}` →
认证包 `041c`（固定密钥 `Redwarhq2018HoneyHoneyHoney`）→ build 包 `041d`。
`uid/secret` 每次由 `qzone.py` 从游戏页 FlashVars 现取。

心跳是 `00 06 04 0e 00 00 00 00`（opcode `040e`），每 10 秒一次。

RC4 的实现在 `tankstorm/crypto.py`，照 `RedWar_2026073102.swf` 的字节码写成：

| 项 | 内容 |
|---|---|
| 密钥中段 | `mid = int(level) * 100 + (0 if firstLogin else 1)` |
| 接收密钥 | `uid ‖ mid ‖ sid`，S 表倒序 `S[k] = 255 - k` |
| 发送密钥 | `sid ‖ uid ‖ mid`，S 表正序 `S[k] = k` |
| 魔改点 | KSA 取模用 `len(key) - 2`；KSA 结束后 `i = j = 11`（均非混淆假分支） |
| 接收豁免 | `0215 0228 0229 0230 0283` |
| 发送豁免 | `040e 041c 041d 0455` |

密钥三要素 `uid/sid/level/firstLogin` **全部来自网页 FlashVars**，socket 还没连就齐了，
所以保活进程能边收边解（见下一节）。

密钥流是连续的：RC4 状态在同方向所有非豁免 body 之间累积，中途漏一条就
永久错位。所以孤立的单个数据包在数学上无法解密，`录制 → 原始流` 也默认开启，
不建议关。

换游戏版本后，`schema.json` 不动（它固定用 2026101403 的编号），而是重跑
`python tools/extract_proto.py <新swf> out` 和
`python tools/build_wiremap.py docs/structure.json out/structure.json <版本>`，
生成该版本的编号对照。2026102102 起游戏更新会打乱 opcode 和字段号，见
[加密与协议还原.md](加密与协议还原.md) 第 7 节。

## 第 2 步：启动保持活跃

```bat
python main.py --keepalive
```

它会：拉取游戏页取最新 openid/openkey/uid/secret → （可选）调 loadIdInfo.war 预热
→ 连 `tankstorm-proxy.sincetimes.com:8001` → 发登录序列 → 每 10 秒发心跳 → 掉线自动
刷新票据重连。`config.json → 保持活跃` 控制间隔、运行时长、重连退避。

闲置踢下线应是 Flash 客户端自己检测鼠标不动后弹广告并断开（客户端行为），
纯 Python 客户端没有这个逻辑，维持 socket 和心跳就能一直在线，这一点已经实盘验证。
若哪天服务器开始主动断开（说明服务端也做了闲置判断，可能需要那个每 10 秒的
0422 轮询包），就要拿当时的日志对照抓包补上对应逻辑。

部署到服务器（Linux）挂后台常驻：

```bash
nohup ~/tank/run_keepalive.sh &     # 或用 systemd / screen / tmux
```

cookie 失效时守护进程会**自动生成新二维码并推送到 PushPlus**（你微信里点开即可看到），
扫码后自动恢复在线，不用你上服务器操作；没扫的话会隔一会儿重发新码。

## 第 3 步：异常事件录制与告警（应对「超级强攻令」）

游戏里别人可以用**超级强攻令**强制进攻你，这种事很随机，没法蹲着抓包。
保活守护进程 24 小时挂在 socket 上，正好顺带做三件事。

双向录制：服务器下行与客户端上行都按帧切好写进 `logs/frames-日期.jsonl`
（高频大包采样，避免日志爆炸）；原始字节流一字不差存到 `logs/streams/<会话>/`
（解密的前提）；重点加密载荷另存 `logs/enc/*.bin`，永不采样、永不截断。

实时解密：密钥三要素在 FlashVars 里就位，连接建立时即可建双向 RC4，边收边解。
启动日志会打印「实时解密已就绪」和自检结果。自检看前 6 条非豁免消息，至少 5 条
解出合法 protobuf 才算通过，否则自动退回"只录不解"，原始流照常保留，
密钥错时不会静默产出垃圾数据。

实时告警通过 PushPlus 推到微信，触发条件如下：

| 触发条件 | 说明 |
|---|---|
| 已确认事件消息 | `027c` RseSuperStormOpt，每次都报，不受"只报一次"/登录静默/已学习影响。`0268` RseCountryOpt 曾在此列，它是国战通用回包，打国战时每秒都在刷，2026-08-29 已移出 |
| 没见过的消息类型 | 主力检测器；登录爆发期只学不报，学到的存进 `logs/known-opcodes.json`，重启后不重复打扰 |
| 消息命中关键词 | 且提到你自己（uid/昵称）才算 |
| 服务器推来图片 | 保留作廉价哨兵，但见下方说明 |

解密启用后，超级强攻的推送会**直接带上进攻方身份**：

```
⚠️ RseSuperStormOpt —— 超级强攻通知
atkName=钢铁洪流｜atkUid=99887766｜deftName=我的基地
```

比一张要眯眼辨认的验证码图片可操作性强得多，你一眼就知道被谁打了。

关键词匹配有个实测踩到的坑：`0283` 是世界广播，正文里全是其他玩家的
自定义昵称。有玩家取名叫「强攻宝贝」「在线包强攻，强攻令2270」，广播一刷就误报。
所以广播类消息只有在提到你自己时关键词才算数；被忽略的命中会记为
`keywords_ignored`，可事后核对。uid 自动填入，也可在 `config.json → 录制 → 我的标识`
里补游戏昵称。

图片检测在本协议上不会命中：还原出的 873 个消息、5582 个字段里
`bytes` 类型为 0 个，socket 根本不传二进制块。名字带 `pic` 的字段全是 `string`，
装的是 QQ 头像标识，客户端拿去走 HTTP 取图。该检测留作通用哨兵，别指望它。

## 第 4 步（可选）：自动拒绝超级强攻

收到超级强攻通知后，除了推送提醒，还可以让守护进程自动发出拒绝包。

`config.json → 录制 → 自动拒绝超级强攻`（默认 `true`）。关掉就退回纯提醒模式。

流程是：实时解密收到 `027c`（RseSuperStormOpt）→ 从解出的字段取攻防双方
uid/昵称 → 构造 `RceSuperStormOpt`（opcode `04ab`）`type=2` → 用 C→S 的 RC4 加密
→ 发送。成功后 PushPlus 会推一条「已自动拒绝超级强攻」，带进攻方名字。

实现在 `sender.py` 和 `proto_encode.py` 里，有三个要点。

- `04ab` 不在发送豁免名单里，body 必须加密。而且**必须复用 Recorder 里那个
  C→S RC4 实例**，另建实例会让密钥流分叉，之后所有非豁免上行包全部作废
- `RseSuperStormOpt` 与 `RceSuperStormOpt` 的字段号不同（Rse: deftUid=3,
  deftName=4, atkUid=5, atkName=6；Rce: atkUid=2, atkName=4, deftName=6, deftUid=7），
  但字段名一致，所以按名取值、按 Rce 的字段号重新编码
- 依赖实时解密已启用且密钥自检通过。自检失败时 `rc4_c2s` 返回 `None`，
  该功能自动跳过并记警告，不会发出错误加密的包污染密钥流

前置条件：

| 条件 | 不满足时 |
|---|---|
| `录制.实时解密 = true` | 拿不到解密后的字段，功能不触发 |
| 密钥自检通过（6/6） | `rc4_c2s` 为 `None`，跳过并告警 |
| `录制.原始流` 保持开启 | 密钥流断裂后无法正确加密上行包 |

> 有一点尚未确认：服务端是否在未完成游戏内验证流程的前提下接受这个拒绝包，
> 目前没有定论，配置项注释里也写明了「若服务端要求先过验证码才接受拒绝，
> 此包可能被忽略」。收到「已自动拒绝」推送不等于确认生效，建议仍旧打开游戏确认结果，
> 直到你自己实测出稳定结论为止。

本项目的边界：脚本做的是观察、解读、通知，以及**复刻客户端已有的协议消息**。
它不识别、不填写、不代答游戏内的人机验证，相关代码库里也不存在。

事后分析：

```bash
python tools/analyze_frames.py --around 19:13     # 某时刻前后 5 分钟
python tools/analyze_frames.py --unknown          # 只看没见过的消息类型

# 离线解密原始流（sid 从同目录 meta.json 自动读）
python tools/redwar_rc4.py logs/streams/<会话>/s2c.bin --uid <你的uid> --write
```

## 第 5 步（可选）：每日任务自动领取

登录后自动发出免费领取类请求。`config.json → 每日任务`。

### 先理解一件事：游戏的确认框保护不了脚本

游戏里消耗勋章会弹"是否消耗"确认框，但那是**纯客户端 UI**，已由 SWF 字节码确认：

- `'是否消耗'` 出现在 `onAllBtn1Click` / `onAllBtn2Click`（按钮点击处理器）
- `'确认购买'` 出现在 `Buytip::processPanel`（面板类）
- 协议里不存在任何二次确认消息，抽奖类消息都是单包完成

脚本直接发包不经过任何对话框，服务器收到就扣。所以参数绝不能猜，
必须在脚本这一侧把危险字段拦死。

### 四层安全机制

| 层 | 作用 |
|---|---|
| 白名单 | 只允许发 `tankstorm/daily/tasks.py` 的 `TASKS` 表里登记的 opcode，表外的连构造机会都没有 |
| 危险字段硬校验 | 字段名命中 `credit/cost/buy/num/cnt/item/card/ticket/discount` 等的，值必须为 0 |
| 状态闸门 | 先读服务器下发的剩余免费次数，`>0` 才发；读不到就保守拒发 |
| 每日次数上限 | 每个任务每天最多 N 次，防逻辑出错循环刷 |

### 为什么需要状态闸门

实测各模块都是**「免费 N 次 + 用完转扣券或勋章」，同一个按钮两种行为**：

| 模块 | 免费额度 | 付费变体 |
|---|---|---|
| 开采石油 / 金属冶炼 | 3/3、1/1 | 第三档 500 勋章 |
| 特工派遣 | 3/3、1/1 | 高级需紫色特工令 |
| 配件探索 | 1/1 | 10次 100 勋章、50次 500 勋章 |
| 军备制造 | 3/3 | 10次 300 勋章、50次 1500 勋章 |
| 矿区探索 | 低/中级 5/5 | 高级 100 勋章 |
| 征战世界 | 免费重征 2/2 | 付费重征 1/1 |

而请求消息里就带着付费字段：`RceWPCExplore.credit`（勋章）、`useItemID`/`useItemCnt`
（"优先使用XX券"那个勾选框）、`RceMineModify.credit`、`RceCountryOpt.costCredit`。

好在服务器会下发剩余免费次数（`RseWPCExplore.leftFreeCnt`、
`RseAdviserDaily.nfreeTimes` 等），所以带 `gate`（闸门）的任务会先读状态再决定发不发。
**读不到状态就不发**，宁可今天不做，也不误扣。

### 参数怎么来：抓包实测，不靠猜

`TASKS` 表里每个任务有 `confidence` 标记，**`待确认` 的默认不执行**。

守护进程录不到你在浏览器里的操作。保活进程和浏览器里的 Flash 是两条独立的
TCP 连接，录制器只录守护进程自己那条。而且一个账号通常只能一个会话，
两边还会互相踢。所以要抓"真实客户端点免费按钮时发了什么"，
必须在**你自己电脑上开游戏 + Wireshark 抓包 + RC4 解密**。

转成 `实测` 的完整流程：

1. 先停掉服务器上的保活（否则两个会话互踢）
2. 浏览器打开游戏，记下 FlashVars 里的 `uid` / `sid` / `level` / `firstLogin`
   （`python main.py --check` 也会打印）
3. Wireshark 开抓，**必须在游戏加载前就开始**（RC4 密钥流从连接建立起累积，
   中途少一个字节后面全解不开）：
   ```
   ip.addr == 193.112.238.18 && tcp.port == 8001
   ```
4. 在游戏里把要自动化的操作手动点一遍
5. 停止抓包 → 右键连接 → 追踪 TCP 流 → 显示为 Raw → 两个方向分别导出
   （上下行密钥不同，不能混）
6. 解密上行并提参数：
   ```bat
   python tools\redwar_rc4.py c2s.bin --uid <uid> --sid <sid> --level <level> --first-login <firstLogin> --write
   python tools\capture_daily.py c2s.bin.decrypted\frames.jsonl
   ```
7. 把打印出的字段值填进 `tankstorm/daily/tasks.py`，`confidence` 改成 `"实测"`
8. 跑一遍 `python -m unittest discover -s tests`，再只开这一项跑一轮 `--daily`，
   对照日志里实际发出的字段

`capture_daily.py` 不带参数时读的是守护进程自己的日志（`logs/frames-*.jsonl`），
那只含**脚本发的包**，用于核对脚本行为，不是你手动操作的记录。

### 执行顺序（重要）

代码强制把**周任务、每日任务排到最后**，前面那些操作本身会推进它们的进度，
先领就漏了。`ordered_tasks()` 保证这一点，改 `TASKS` 表的顺序也不会破坏。

### 默认配置

默认开关以 `config.json` 的 `每日任务.任务` 为准，`python main.py --list` 能看到
每一项的开关和今日进度。参数已抓包实测的默认开启，「待确认」的（每日资源、战功排名、
月卡领取、周任务）保持关闭。

「免费次数用完自动购买」在代码层面禁止，`nbuycnt` 这类字段非零直接拒发，
不提供开关。唯一的例外是功勋商城补支援兵：它用功勋付款，默认关闭，自带一套对账防线，
见 README。

## 社交 HTTP 任务（已移除）

好友赠礼/邀请/召回是现成 HTTP 接口（`joyorder.war`/`receiveGift.war`/`recall.war`）。
本项目早期用 `endpoints.json` 模板回放这类请求，那套 HTTP 任务引擎一直没有配上
可用的请求，已经移除。核心游戏任务（签到/领奖/抽奖）走 socket。

## SWF 逆向工具链

协议还原不再依赖抓包猜测，可以直接从 SWF 字节码读出来。四个工具都建立在
`abcparse.py`（ABC 结构解析）+ `disasm.py`（AVM2 反汇编）之上：

```bash
# 还原全套协议：opcode 表 + .proto + schema.json
python tools/extract_proto.py RedWar_xxx.swf out

# 按类名反汇编，看成员和方法体
python tools/dump_class.py RedWar_xxx.swf Transport
python tools/dump_class.py RedWar_xxx.swf _-0ly --only encrypt,init

# 全库交叉引用：哪里引用了某个字符串
python tools/xref.py RedWar_xxx.swf --string rc4
```

对 `RedWar_2026073102.swf` 的实测规模：4482 个类、62967 个方法、74216 条常量池
字符串，完整解析约 2.3 秒（带磁盘缓存，二次加载秒开）。

SWF 被 secureSWF 混淆（类名变成 `_-4I4` 这种），但混淆器动不了字符串字面量和
数值常量，协议还原正是靠这两点：protobuf-as3 的报错模板
`Bad data format: <消息名>.<字段名> cannot be set twice.` 泄露了全部消息名和字段名，
`toString()` 里的 `'rc4'` 字面量坐实了加密算法。方法论见
[protocol-reverse-engineering.md](protocol-reverse-engineering.md)，
完整过程见 [加密与协议还原.md](加密与协议还原.md)。

## 下一步 / 说明

- 仅保活：只需第 1~2 步。这是当前主目标，已实盘验证可用。
- 保活 + 事件感知：加上第 3 步，被打时能第一时间知道是谁。
- 第 4 步是可选的主动响应，默认开启；只想要提醒的话把
  `录制.自动拒绝超级强攻` 设为 `false`。
- 每日任务：现在有了 873 消息的 schema（其中 `Rce*` 客户端请求 232 个、
  `Rse*` 服务器响应 295 个），签到/领奖/抽奖对应哪个消息、字段怎么填都能查表，
  比早期靠抓包猜的路子好走得多。
- 会封号吗？行为等同你自己挂机在线，风险低，但毕竟是自动化，自行权衡。
- 游戏改版/换服务器：用 `extract_proto.py` 和 `build_wiremap.py` 生成新版本的编号对照，
  必要时重抓包更新 `protocol.json`。

## 项目定位

维持自己账号的在线状态、把服务器发生的事及时解读并通知到你本人。观察、录制，
再到分析和告警，到此为止；游戏内的人机验证由你本人处理。
