# 坦克风暴：加密机制与协议还原

全部结论来自 `RedWar_2026073102.swf` 的 ABC 字节码反汇编，可用 `tools/` 下的
脚本复现。SWF 被 secureSWF 混淆过（标识符重命名 + 不透明谓词造假分支），
下文的伪代码都是**去掉假分支之后**的真实控制流。

复现命令：

```bash
python tools/dump_class.py RedWar_xxx.swf ":Transport"      # 反汇编整个类
python tools/xref.py       RedWar_xxx.swf "_-1yo"           # 全库交叉引用
python tools/extract_proto.py RedWar_xxx.swf out            # 还原协议
```

---

## 1. 帧格式

```
[u16be 长度 N][u16be opcode][u32be seq][body]      整帧 = 2 + N
```

`N` 覆盖 opcode(2) + seq(4) + body。**包头永远是明文**，只有 body 可能加密。

---

## 2. 加密范围：按 opcode 白名单

`Transport.Send`（发送）：

```as3
op = _-5sY._-7CF(msg);
ba = new ByteArray(); ba.endian = BIG_ENDIAN;
msg.writeExternal(ba);
if (op != 0x040E && op != 0x041C && op != 0x041D && op != 0x0455)
    _-4I4.encrypt(ba);                       // 白名单之外才加密
header.length = ba.length + 6; header.type = op;
_-0Ig._-Sr(header); _-0Ig.writeBytes(ba); _-0Ig.flush();
```

`Transport._-29U`（socket 数据处理，接收）：

```as3
socket.readBytes(ba, 0, _-55i);
if (op != 0x0215 && op != 0x0228 && op != 0x0229 && op != 0x0230 && op != 0x0283) {
    decode(ba);                              // decode() 里是 _-1yo._-2Sm(ba)
    ba.position = 0;
}
msg.readExternal(ba);
```

豁免名单查表之后语义完全自洽——全是心跳和广播：

| opcode | 消息 | 方向 |
|---|---|---|
| 040e | RceHeartbeat | 发送 |
| 041c | RceInit | 发送 |
| 041d | RceLoad | 发送 |
| 0455 | RceDebug | 发送 |
| 0215 | （空消息，pong） | 接收 |
| 0228 | RseSysBroadcast | 接收 |
| 0229 | RseWebBroadcast | 接收 |
| 0230 | RseComBroadcast | 接收 |
| 0283 | （单字段广播类） | 接收 |

`protocol.json` 里静态重放的心跳/认证/build 恰好都在发送豁免名单里——这是重放
能工作的原因，**不能据此认为协议没加密**。同理，0283 世界广播能读出中文昵称，
也只是因为它在接收豁免名单里。

## 3. 密钥流范围（最关键的一点）

* 包头永远不过 RC4
* 豁免消息的 body **完全不碰 RC4 实例**，不消耗密钥流
* 每个方向一个 RC4 实例，登录响应到达时建立，之后再不重置

所以密钥流在「该方向所有非豁免 body」之间**连续累积**。要解第 N 条，必须按顺序
把它之前的每一条非豁免 body 喂进同一个 RC4 实例，一条不能少；而包头和豁免
消息必须排除在外。

**中途漏一个非豁免 body，之后全部永久解不开。** 这就是为什么必须全量录原始流，
以及为什么分帧失步是致命错误。

---

## 4. 密钥推导

`Transport._-3rU` —— **注意它不是 socket 消息处理器**，全库只有一个调用点，
在 `RedWar.Data`（网页传进 SWF 的 FlashVars 设置器）里。也就是说密钥材料全部
来自网页参数，socket 还没连就已经算好了：

```as3
_-0fk = msg.level;
_-0MJ = msg.sid;
_-0tS = new SecNum(String(msg.firstLogin) == 'true' ? 0 : 1);
_-2q0(int(_-0fk * 100 + _-0tS.Get()));       // 密钥第三段
```

`Transport._-2q0(mid)`：

```as3
if (_-0MJ != null) {
    _-5nc = BASE._-71r + mid + _-0MJ;        // 接收密钥
    _-08k = _-0MJ + BASE._-71r + mid;        // 发送密钥
} else {
    _-5nc = _-08k = BASE._-71r;              // 兜底
}
_-1yo = new RC4(utf8(_-5nc), true);          // 接收，S[k] = 255 - k
_-4I4 = new RC4(utf8(_-08k), false);         // 发送，S[k] = k
```

AS3 里 `String + int` 是十进制拼接，所以中段是 `str(level*100 + firstLoginFlag)`。

> ⚠️ **`firstLogin` 不是"这个账号第一次登录"，而是"今天还没真正进过游戏"。**
> 2026-08-30 实测对照：当天头一回打开游戏页时 FlashVars 给 `true`；只开页面
> 不会改变它；用 socket 真正登录并玩了一轮之后，再开页面就变成 `false`。
> 也就是说这个标记由**真正的 socket 登录**消费掉。
>
> 它直接决定密钥中段：`level=35` 时，当天第一次进游戏是 **3500**，
> 之后再连是 **3501**。离线解密老抓包时，要按录制那一刻的取值来，
> 不能一律当成 `false`。

**推论**：`uid` / `sid` / `level` / `firstLogin` 四个值都在 FlashVars 里
（本项目的 `qzone.py` 本来就在抽这四个），所以保活进程在 connect 时就能把密钥
算出来、边收边解，不需要事后离线跑。见 `tankstorm/crypto.py:from_ctx()` 和
`Recorder.enable_crypto()`。

`BASE._-71r`：`BASE::cinit` 里默认 `'780511549720865'`，但 `RedWar.Data` 在运行时
会把它覆盖成 **uid**。所以实际密钥基本上是 uid 打头。

## 5. RC4 实现（`_-15y:_-0ly`，`toString()` 返回 `'rc4'`）

```
init(key:ByteArray, reversed:Boolean):
    for k in 0..255: S[k] = reversed ? 255 - k : k
    j = 0
    keylen = key.length - 2                  # 无条件，不是假分支
    for k in 0..255:
        j = (j + S[k] + key[k % keylen]) & 255
        swap(S[k], S[j])
    i = 11; j = 11                           # 无条件，不是假分支
```

三个"非标准"点里，`len-2` 和 `i=j=11` 都是真的；S 表的两个版本不是假分支，
是构造函数第二个参数控制的——接收倒序、发送正序。

## 6. 协议还原

* **opcode 表**：`_-1JW::_-67s` 里有 563 次 `_-055(opcode, 消息类)` 注册调用，
  opcode 是 `base + offset` 的立即数。
* **消息真名**：protobuf-as3 生成的报错模板
  `Bad data format: <消息名>.<字段名> cannot be set twice.` 是字符串字面量，
  混淆器动不了。按类扫这些字符串即可映射回真名——873 个全部还原。
* **字段号**：在 `writeToBuffer`（不叫 `writeExternal`）里，
  `writeTag(output, wiretype, <tag>)` 的 tag 是立即数。
* **字段类型**：`WriteUtils(_-3EJ)` 一半方法被混淆了，靠方法体实测认定：
  `_-9g`=writeTag，`_-1lP`=double，`_-6pT`=float，`_-30c`=bool(writeByte)，
  `_-yF`=string(writeUTFBytes)，`_-6YX`=bytes(length+writeBytes)，`_-jt`=enum，
  `_-1CD`=message，`_-AL`=group。

产物：`docs/redwar.proto`（873 个 message、5582 个字段）、`docs/opcodes.json`、
以及给代码用的 `tankstorm/schema.json`。

关键消息：

```protobuf
// opcode 0x027c
message RseSuperStormOpt {
  optional int32  type     = 1;
  optional int32  nResult  = 2;
  optional string deftUid  = 3;   // 被攻击方 uid
  optional string deftName = 4;   // 被攻击方名字
  optional string atkUid   = 5;   // 进攻方 uid
  optional string atkName  = 6;   // 进攻方名字
}
```

`0x0268 = RseCountryOpt`（国家事件通告），实测与 027c 同时到达。

## 6.5 协议里没有图片

全协议 **0 个 `bytes` 类型字段**——socket 上不传任何二进制块。
`RseInit.picSquare`、`RseOfficerOpt.pic`、`RceAttack.attackPic` 这类字段全是
`string`，装的是 QQ 头像标识，客户端拼成 `thirdapp1.qlogo.cn/qzopenapp/<hash>`
再走 HTTP 取图。游戏内的图片资源要么内嵌在 SWF，要么在
`app100616028.imgcache.qzoneapp.com` 这个 CDN 上。

所以 `recorder.py` 里的 `IMAGE_MAGICS`（PNG/JPEG/GIF 魔数检测）在这个协议上
永远不会命中。留着当廉价的兜底哨兵可以，但别指望它。

## 7. 版本绑定

以上全部绑定 `RedWar_2026073102.swf` 这一版。游戏更新后 opcode 可能整体平移、
豁免名单可能变化。重新生成：

```bash
python tools/extract_proto.py <新的.swf> out
cp out/schema.json tankstorm/
cp out/redwar.proto out/opcodes.json docs/
```

豁免名单在 `tankstorm/recorder.py` 的 `EXEMPT_OPCODES` 和
`tools/redwar_rc4.py` 的 `EXEMPT`，需要时用
`python tools/dump_class.py <新swf> ":Transport"` 重新核对
（看 `Send` 和 `_-29U` 里的 `pushshort` 比较链）。

录制器有个交叉校验：豁免名单说该明文、实测却是高熵密文时会告警提示
"游戏可能改版，白名单需要重新逆向"。
